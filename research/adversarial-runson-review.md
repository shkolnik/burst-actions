## (a) Verified facts about RunsOn

**Licensing & source model**
- Free license for "nonprofit, open-source, educational, and personal non-commercial projects"; sole condition is "a public acknowledgement linking back to runs-on.com". Free tier includes full product (Flex + Fleet, all public binaries and AMIs). **[V]** (runs-on.com/pricing, 2026-08-08)
- Commercial licenses are flat annual per-entity fees from €300/yr. A license *key* is required at install even for the free/trial path; the 15-day trial collects payment details. **[V]** (pricing + quickstart)
- The public GitHub repo (runs-on/runs-on, ~1.3k stars, ~750 commits) is **MIT-licensed CloudFormation assets and supporting files only**. The **server and agent are commercially licensed, closed binaries**; "full server & agent source-code access" is an **Enterprise-tier** (€3,600/yr) perk. **[V]** (github.com/runs-on/runs-on, pricing, 2026-08-08)

**Architecture (v3, current)**
- One CloudFormation stack in *your* AWS account; no vendor-hosted control plane; a **private GitHub App** created during install lives only in your account. Works for a **personal GitHub account** (username in place of org name). **[V/R]** (quickstart; install docs via search)
- v3 (2026) control plane: **API Gateway + Lambda ingress, plus a single ECS/Fargate runtime task** (FARGATE_SPOT optional to cut idle cost, at the price of brief control-plane gaps until spot capacity returns; interrupted queue messages retry via SQS visibility timeout). Replaced App Runner because **AWS put App Runner into maintenance mode 2026-03-31**. v3 was a **breaking release**; recommended migration is blue-green (run both stacks, then delete v2). **[V]** (runs-on.com/blog/the-road-to-v3/)
- Ancillary resources: SQS queue, SNS alerts, CloudWatch logs/metrics, S3 buckets. Stack idle cost claimed "about one or two dollars a month." **[R]** (stack-config/site via search summary — treat the exact figure as a vendor claim)
- Per-job **ephemeral EC2**: fresh instance per job, ~30s boot from their maintained public AMIs, terminated on completion; **spot with automatic on-demand fallback**. Composable label syntax (`runs-on=${{github.run_id}}/runner=2cpu-linux-x64`, `cpu=4/ram=16/family=...`). **[V]** (homepage, quickstart)
- Install: ~15 minutes total — CloudFormation quick-create (org/username, license key, email; creates "a dedicated IAM role with minimal required permissions"), then register the GitHub App via the stack's `RunsOnEntryPoint` URL, then change workflow labels. Dedicated AWS **sub-account recommended** by RunsOn itself. **[V]** (quickstart)

**Cleanup / edge-case machinery**
- Server force-terminates any instance **not tagged with a job within 15 minutes of launch**; a separate **10-minute agent-side watchdog** covers agent-launch failure; a server-side **housekeeping loop** cleans "dangling instances" and turns `runs-on-terminate=true` into actual EC2 termination (v3 made finalization faster). **[V/R]** (changelog v2.3.1 + "what's new in v3" via search)
- Observability: per-job cost tracking, CloudWatch metrics, OpenTelemetry traces. **[V]** (docs index)
- Caching: "Magic Cache" (S3-backed, claimed 5× faster than GitHub's, unlimited), and **v3.2.0 (2026-08-04) "sticky disks"** — persistent EBS build-cache volumes with snapshot restore, via a `sticky=` label. **[V]** (changelog)

**Maintenance cadence**
- Releases roughly every 1–4 weeks through 2025–2026; v3.2.0 on 2026-08-04 (four days before this review); v2.12.x still receiving backports in parallel with v3. **[V]** (changelog)
- Bus factor: RunsOn is widely described as a small/solo-developer product (HN launch thread exists), but I could not verify current team size from primary sources. **[U]**

## (b) The strongest case for RunsOn, itemized

1. **The doc's own exclusion test convicts the doc.** §4: *"The test for every exclusion: does its failure mode cost more maintainer attention than its absence costs money or risk?"* Apply it to the build itself. RunsOn's "failure mode" is a closed binary in a scoped IAM role inside a disposable sub-account; its cost is 15 minutes of setup and ~$1–2/mo — **the same order as the DIY design's own idle cost** (§3: snapshot ~$1.25–2/mo). The DIY's cost is weeks of the one genuinely scarce resource. The requirements section says "Prefer a mature existing tool over invention"; the doc then invents, on a single objection (examined in point 5).

2. **Rollout step 2 is the tell: the DIY plan's hardest work is re-deriving what RunsOn already survived.** The doc itself says *"The layers are only real once each has been observed firing"* and schedules deliberate kill-testing of every layer (kill CLI mid-launch, broken AMI, hung job, cancelled run, spot reclaim). That is exactly the multi-year edge-case ledger visible in RunsOn's changelog: the 15-min server-side untagged-instance kill, the 10-min agent watchdog, the dangling-instance housekeeping loop, v3's faster finalization of completed runners, spot→on-demand retry. Every one of these is a lesson the DIY tool must **re-learn empirically**, and the doc's failure-mode table (§ Cleanup) is a *prediction*, not an observation. The class of bugs that live between "designed" and "observed firing" is precisely where a mature product's value is concentrated.

3. **"Still works in two years untouched" favors the maintained product, not the frozen one — and RunsOn has already demonstrated it.** The hard requirement is durability under neglect. The DIY tool untouched for two years faces: GitHub runner-agent churn (the doc's own mitigation is a monthly surprise 10–20 min rebake keyed on agent version), GitHub REST quirks (§5 already documents one: per-run job-label enumeration), Ubuntu base-AMI drift, `aws-sdk-rust` churn, and AWS platform deprecations. RunsOn just absorbed a worst-case instance of that last category *for its users*: AWS killed App Runner and RunsOn shipped a rebuilt control plane before the deadline. Nobody performs that rescue for `burst`. "Durable" and "untouched" are in tension for owned code; a maintained dependency is the resolution.

4. **The acknowledged decay in the DIY image story is already solved upstream.** The doc concedes the baked `target/` "drifts stale against main without changing the key" and defers the fix (sccache phase 2) until after measurement — while noting one-job-per-VM *raises* its value. RunsOn ships both halves today: Magic Cache (S3, unlimited) and, as of four days ago, sticky-disk EBS build caches. The DIY plan's phase 2 is RunsOn's shipped feature; the DIY plan's AMI bake/rebake machinery (`bake`, content-address key, generation GC, builder-VM custody) is ~a third of the tool's surface and RunsOn users simply don't have it — maintained AMIs are part of the free tier.

5. **The rejection sentence does not survive inspection.** *"Third-party code holding EC2 rights in our account"* conflates three separable things:
   - **What holds the rights**: an IAM role created by an **MIT-licensed, fully inspectable CloudFormation template** in the public repo. The grant is readable, diffable across releases, and scopeable before deploy; RunsOn advertises (and the template shows) minimal permissions. The *rights* are not opaque even though the *server binary* is.
   - **Blast radius**: RunsOn's own recommended install is a **dedicated sub-account** — which reduces "third-party code in our account" to "third-party code in a purpose-built empty account whose only contents are CI runners." That is a *smaller* trust surface than `burst` running with James's dev-machine AWS credentials broad enough to create IAM roles, EventBridge schedulers, AMIs, SGs, and budgets in the main account.
   - **Compared to what**: the DIY alternative is *also* code holding EC2 rights — freshly written, partly by AI agents, reviewed by the same single maintainer who is its only auditor and only tester. "Code I can read" is only a security win if the reading (and the kill-testing, and the re-reading after every change) actually happens, forever. The doc's own culture (CLAUDE.md: never trust a subagent's report; prove teeth by regressing production) prices that auditing honestly — and it is expensive.

6. **Operationally, the mature tool is *simpler* for the stated user, not more enterprise.** The doc's anti-enterprise instinct is aimed at ARC/k8s and philips-labs/Terraform, and lands. But RunsOn-Flex is: one CloudFormation stack, one GitHub App, change a label. No `burst` binary to build, keep prebuilt ("CI is broken must never block launching CI runners" — with RunsOn there is no local binary in the loop at all), no statefile/flock/adoption semantics, no cross-host advisory-collision protocol, no IAM eventual-consistency retry lore, no quota-warn logic (spot fallback is automatic). §3's concurrency-and-resumption paragraph alone — lockfiles, torn-state renames, abandoned-run adoption, incompatible-command reconciliation — is a page of subtle design that exists *only because* a human-launched watcher exists. Webhook-driven autoscaling deletes the entire problem class: push, and the right number of VMs appear, per job, with no watcher to kill, detach, or adopt.

7. **`--auto` is a strictly worse re-implementation of what a webhook does natively.** The doc sizes the fleet by polling queued jobs at launch time (with a documented N+1 API-call wrinkle) and explicitly forgoes mid-flight rescaling — a second push mid-burst needs a human/agent to run `up` again. RunsOn receives `workflow_job` events and launches per job: correct sizing by construction, including for pushes that arrive after the burst started. The "one command" UX the requirements ask for becomes **zero commands**.

8. **Credential posture is comparable, not worse — and one part is better.** The DIY plan's PAT is a long-lived fine-grained PAT on the dev machine with runners:write. RunsOn's credential is a **private GitHub App** (short-lived installation tokens, revocable as a unit, never on a laptop) living in the same AWS account as the stack **[V for privateness; token mechanics U]**. Per-VM, both designs give the instance only ephemeral registration material and register one runner per job. The DIY plan cannot claim an advantage here without auditing RunsOn's agent — but symmetrically, it hasn't shown a deficiency.

## (c) Where the case is weak / where the doc survives

Honesty requires conceding four real points:

1. **Invariant 1 is violated as literally written.** "No daemon, webhook receiver, Lambda, or warm pool. Ever." RunsOn v3 has all three of the first: API Gateway + Lambda ingress and a standing ECS/Fargate task. It is scale-to-zero *runners*, not scale-to-zero *everything*. The ~$1–2/mo idle cost is a vendor claim I could not itemize **[R]**, and a standing webhook endpoint is standing attack surface (mitigated by managed WAF in v3, but present). If James's invariant is a genuine principle rather than a proxy for "nothing to babysit + nothing bills," RunsOn loses on it, full stop. My advocate's response — that a Fargate task AWS restarts for you is not "babysitting," and the DIY design *also* pays ~$2/mo idle — is an argument about the invariant's *intent*, and intent is James's to adjudicate, not mine.

2. **The cleanup guarantee is architecturally weaker in one specific way, and unauditable.** The DIY's layer 1 (EventBridge one-shot `TerminateInstances` armed at launch) is *instance-independent and server-independent* — pure AWS control plane. RunsOn's verified cleanup layers (15-min server kill, housekeeping loop) **depend on the RunsOn server task being alive**; whether an equivalent VM-and-server-independent hard kill exists I could not verify, and — the sharper point — **cannot verify without Enterprise source access**. For a maintainer whose culture is verify-by-running, "the binary probably reaps correctly" is exactly the kind of claim the doc's invariant 3 refuses to take on faith. This is the strongest surviving pillar of the build decision.

3. **Closed source is a real cost for this specific user, beyond security.** The free tier's server and agent are binaries. The beep project's norms (fail-loud forensics, live A/B against OLD binaries, reading the code when behavior surprises) don't work against a black box. When a runner misbehaves mid-benchmark, the DIY tool is greppable; RunsOn is a support thread. Also a nonzero tail risk: license terms can change, the (probably very small **[U]**) company can die — self-hosted means the stack keeps running, but updates stop and the MIT part alone is not forkable into a working product. And the v2→v3 breaking migration proves the "touch it every couple of years" event *does* happen with RunsOn too — it's just someone else's schedule.

4. **Fit frictions.** The free license requires a public acknowledgement linking to runs-on.com (trivial but nonzero, and a term that could change). Install wants a license key and (for trial) payment details. Label scheme differs from the doc's `[self-hosted, burst]` home-runner coexistence plan (coexistence is still achievable — everyday CI keeps targeting `home` — but the routing section would be redesigned around RunsOn's label grammar). The doc's invariant-5 preflight (hard-error if fork approval is weak) is a bespoke nicety RunsOn presumably lacks **[U]**; the underlying repo setting protects both designs equally.

Points I considered and *rejected* as attacks on RunsOn: setup effort (15 min, verified, trivially beats building anything); "enterprise system" (it isn't — that label fits ARC/philips-labs, not one CFN stack); vendor-hosted-control-plane risk (there is none — verified self-hosted); personal-account support (verified works).

## (d) Bottom line as advocate

**For RunsOn to win, the following must be true — and most of it demonstrably is:**
1. The real requirement behind invariant 1 is "nothing to babysit, nothing meaningful bills at idle" rather than the letter "no Lambda ever" — *plausible but reserved to James; this is the decision*.
2. The maintainer's attention is the binding budget — *the doc itself asserts this in §4, and the DIY plan spends weeks of it, including a kill-testing campaign whose entire purpose is to reproduce maturity RunsOn already has*.
3. "Third-party EC2 rights" can be bounded to acceptability — *verified: inspectable MIT IAM template + RunsOn's own recommended dedicated sub-account reduces the blast radius below that of the DIY tool running with substrate-creating credentials in the main account*.
4. Non-commercial licensing is free and stable enough — *verified free with an attribution link; stability is a judgment call*.
5. The unauditable server-dependent cleanup path is acceptable given a sub-account + an independent AWS budget alarm (which the user can arm themselves in 5 minutes, replicating the DIY's layer 5 outside RunsOn entirely) — *the honest residual risk: a wedged RunsOn server + a wedged instance with no EventBridge backstop; bounded in dollars by the alarm, but a genuine step down from the DIY's layer-1 guarantee*.

**Verdict:** On cost, setup, edge-case maturity, cache story, sizing correctness, and two-year durability, the evidence supports RunsOn over the DIY plan, and the doc's stated rejection sentence does not hold up — the "EC2 rights" objection dissolves under the sub-account + inspectable-IAM analysis, leaving only "the small owned alternative exists," which is a preference, not a reason. The build decision's *actual* load-bearing supports are two things the doc undersold: the literal scale-to-zero invariant (a standing webhook stack exists in RunsOn, full stop) and the **auditability of the cleanup guarantee** (EventBridge one-shots are provable; a closed server's housekeeping loop is not, below €3,600/yr). If James reads invariants 1 and 3 as principles, build stands on those two legs — but the doc should then say *that*, and drop the pretense that the objection is about third-party EC2 rights. If he reads them as proxies for "no babysitting, no leaks that cost real money," RunsOn wins on the maintainer-attention arithmetic the doc itself endorses, and the already-designated fallback should be the first choice, not the consolation.
